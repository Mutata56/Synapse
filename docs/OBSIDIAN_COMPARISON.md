# Obsidian и Synapse как реализованы основные функции

Obsidian строит работу вокруг текста Markdown, путей файлов и отдельного кеша структуры документа. Блочный редактор Synapse хранит JSON документа BlockNote и Markdown-представление; связи в графах преимущественно определяются по заголовкам. Поэтому перенос файлов требует собственного режима Markdown, который сохраняет исходник без преобразования в блоки.

Сравнение относится к установленному Obsidian 1.13.7 и Synapse на основе коммита `67578d2630da617d883ad91b5573880465e873c2`, включая изменения для импорта от 10 октября 2026 года. Исследованы хранение, редактор, метаданные, ссылки, теги, поиск, граф и Canvas. Оценок скорости по внешнему виду реализации здесь нет.

## Сравнение реализаций

| Функция | Obsidian | Synapse | Практическое следствие |
|---|---|---|---|
| Хранение и изменения файлов | `FileSystemAdapter` ставит операции в очередь Promise; `Vault` ведёт карту файлов, кеш текста и события create, modify, delete, rename. Внешние изменения приходят через `fs.watch`. | Файловые команды Tauri, Markdown на диске, JSON-кеш метаданных и кеш ссылок. | У Obsidian файловые изменения и обновление производных данных связаны общей системой событий. |
| Редактор | CodeMirror хранит текст документа; `get()` возвращает `state.doc.toString()`. `TextFileView` сохраняет текст через `Vault.modify`. | Обычные заметки: BlockNote и ProseMirror, JSON блоков плюс Markdown и его hash. Импортированные заметки: отдельный редактор полного исходника и ReactMarkdown для чтения. | Mermaid, YAML, callouts и формулы в импортированных файлах сохраняются как исходный текст. Они не проходят через `blocksToMarkdownLossy`. |
| Сохранение и конфликты | В просмотренном пути debounce 2 секунды, сравнение с сохранённым текстом, очередь записи, backup при ошибке; внешнее изменение при локальных правках передаётся функции с baseline, local и incoming. | Блочный редактор использует debounce 400 мс. Новый исходный режим сохраняет после паузы 600 мс и при навигации, держит локальный черновик и проверяет исходную ревизию перед записью. | При конфликте исходный режим сообщает об ошибке и сохраняет черновик. Автоматическое слияние трёх версий пока не реализовано. |
| Структура Markdown | `MetadataCache` проверяет mtime и размер, вычисляет SHA-256 изменённого файла, хранит file и metadata в IndexedDB. Отдельный Worker разбирает YAML, ссылки, embeds, теги, заголовки, секции, задачи, block IDs и позиции. | Метаданные извлекаются функциями в `storage.ts`; полнотекстовые тела дополнительно кешируются в памяти. | Для совместимости с синтаксисом Obsidian полезен единый структурный разбор с позициями, а не несколько независимых регулярных выражений. |
| Wiki-ссылки и алиасы | Resolver работает с путями: расширение, относительные ссылки, точный путь, suffix matches и предпочтение папки источника. Suggestions показывают aliases вместе с каноническим файлом. | В блочном режиме ссылки остаются текстом с ProseMirror decorations; навигация исторически ищет заголовок. Исходный режим отдельно разрешает точный путь, путь относительно заметки и уникальный basename. | `[[Папка/Заметка#Раздел\|подпись]]` может сохраняться без переписывания. Preview поддерживает переходы по путям и заголовкам, но resolver ещё не повторяет весь алгоритм Obsidian. |
| Backlinks | Ссылки разрешаются относительно файла-источника; кеш хранит counts по resolved и unresolved путям. Backlinks содержат реальные ссылочные записи. | `computeBacklinks` сопоставляет строки `NoteMeta.links` с заголовком; `count: 1` означает наличие связи из заметки. | В Synapse пока нет полноценного списка всех вхождений с позициями. Одинаковые заголовки неоднозначны. |
| Теги | YAML и структурно распознанные inline tags; подсчёт родителей иерархических тегов, объединение вариантов регистра. | Текстовые decorations для inline tags и агрегация `NoteMeta.tags`; импорт учитывает доступные tags из YAML. | Согласованный parser и правила иерархии пригодятся для тегов `#работа/склад` и поиска по ним. |
| Поиск | Лексер и дерево matcher-ов: AND, OR, отрицание, скобки, regex, property queries, операторы path, file, content, line, block, section, task, tag. Матчеры указывают, какие данные нужно прочитать; поиск отменяется. | Поиск подстроки без учёта регистра по заголовку и сырому Markdown body. Заголовок получает больший вес; холодное чтение тел идёт пулом из 8. Fuse используется в других путях интерфейса. | Запрос `path:RoadMaps task-todo:` сейчас требует отдельного языка запросов в Synapse; его нельзя считать обычным текстовым поиском. |
| Глобальный и локальный граф | Узлы задаются путями из resolved и unresolved links, возможны tag и attachment nodes. Pixi рисует граф, общий симулятор работает в Web Worker; `sim.js` содержит WASM-путь и D3 fallback. | Graphology с узлами папок и заметок; Pixi, папочные кластеры и собственный CPU `ForceLayout` в потоке интерфейса. Активный локальный граф также WebGL. | Вынос физики в Worker уменьшит конкуренцию с интерфейсом. Статический код не доказывает, какой движок быстрее на этом vault. |
| Canvas | Отдельный JSON `.canvas` с nodes и edges. Типы file, text, link и group; неизвестные поля сохраняются. Карточки — DOM, связи — SVG; пространственные индексы и виртуализация видимой области. File nodes используют живые Markdown, PDF и медиа-вложения. | Собственный `Board {shapes, edges, camera}`, два Canvas2D слоя и JS engine. Snapshot живёт в props блока BlockNote; Markdown-представление блока — `[Доска]`. NoteNode хранит текст, не путь к заметке. | Для импорта `.canvas` нужен явный адаптер схемы и семантики вложений. Простое переименование в whiteboard snapshot некорректно. В текущем vault файлов `.canvas` нет. |

## Что изменено для переноса

Все 666 файлов vault скопированы в `~/Library/Application Support/com.kirill.synapse/notes`: 530 Markdown-файлов, остальные вложения, файлы и конфигурация Obsidian. Имена и вложенность сохранены; SHA-256 каждого исходного файла совпал с копией. Исходное приложение и vault находятся отдельно от рабочих данных Synapse.

`.synapse/obsidian-import.json` отмечает происхождение заметок. Метаданные интерфейса хранятся в `.synapse/obsidian-metadata.json`, поэтому установка избранного, заголовка, иконки или обложки не пересобирает YAML исходного файла. Признаки исходного режима и метаданные переносятся при перемещении, переименовании папок, помещении в корзину и восстановлении.

Новый режим находится в `MarkdownSourceEditor.tsx`; общие функции исходника, ссылок и preview — в `obsidianImport.ts`; файловые проверки и sidecar — в `storage.ts`. Полный Markdown, включая YAML и исходные окончания строк, сохраняется отдельно от текстового тела для поиска.

Файлы и настройки плагинов сохранены как данные. Их код не запускается через API Obsidian внутри Synapse. В preview Mermaid и математический синтаксис пока отображаются как исходный код или текст; редактирование не удаляет их.

## Что стоит улучшить дальше

1. Общий resolver для preview, редактора, глобального графа, локального графа и backlinks с идентичностью по пути. Сейчас global graph выбирает первую заметку с одинаковым заголовком, local graph связывает каждую, backlinks также могут показываться для каждой.
2. Структурный Markdown parser с positions, headings, block IDs, tags и YAML; обновлять кеш по изменению файла.
3. Язык поиска с path, tag, property и task operators поверх текущего кеша тел.
4. Worker для физики графа с обменом typed arrays. Перед выбором алгоритма измерить latency интерфейса, время шага и расход памяти на одинаковых данных.
5. Рендер Mermaid и формул в исходном режиме, затем явный адаптер `.canvas`, если появится такой контент.

Два риска исходной доски Synapse заслуживают отдельной проверки: последний штрих может не попасть в block snapshot при закрытии внутри первого debounce; подпись соседнего узла локального графа может остаться прежней после переименования, когда структура графа не изменилась. Это выводы из кода, поведение в работающем приложении здесь не воспроизводилось.

Хэши оригинала и нашей копии совпадают. Выводы о функциях renderer относятся к отдельно проверенному `obsidian.asar` и его JavaScript.
